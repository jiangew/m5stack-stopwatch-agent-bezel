# 四个 Agent 桌面功能诊断（2026-10-10）

## 行为判据

左滑固定循环：首页 → Codex → DeepSeek → SUPER → Hermes → 首页。

| 目标状态 | 左滑选择桌面 | 中央点按 | 上、下、右 |
| --- | --- | --- | --- |
| 未启动 | 等待，不启动应用 | 启动所选应用 | 确认目标前台后启用 |
| 已在前台 | 直接启用 | Codex 保持原 Send；其他三个无动作 | 保持各自原映射 |
| 已运行但在后台 | 等待，不抢前台 | 唤起目标 | 确认目标前台后启用 |
| 操作中切走目标 | 保留所选 Agent，回等待状态 | 再次唤起 | 不发给其他应用 |
| 启动失败或超时 | 保留所选 Agent 的重试状态 | 显式重试 | 等待期间禁用 |

## 诊断结果

- 实机旧版日志在 DeepSeek、Hermes 的方向输入后记录 `accessibility_rejected`。
  辅助功能开关重开后仍被拒绝；旧进程重启后另报告输入监控未授予。
  因此必须验证当前已安装程序的有效授权，不能只看系统设置开关。
- Codex 使用原生输入路径，另三个使用进程定向按键，需要 Companion 辅助功能权限。
- DeepSeek 导航插件 0.1.1 已安装。SUPER 当前和旧 bundle 均保留支持。
- 旧状态逻辑会在左滑时激活部分后台应用、强制 Hermes 等待、拒绝部分 SUPER
  后台中央唤起，并在前台切换时替换手表所选桌面。build12 修复这些差异。
- 另观察到额度接口网络失败，以及一份旧版 AppServerClient 写管道崩溃记录。
  本次导航修复未声称解决该独立问题；额度成功不能替代导航验收，反之亦然。

## 修改与验证范围

修改 Mac Companion 状态机并增加启动时权限日志，复用现有五屏固件和手势协议。
不改变各 Agent 的导航映射、Home 主题和 Codex 仪表盘。

自动验证包括四个 Agent 三种状态、前台通知竞态、退出检测、Hermes 窗口聚焦、
SUPER 无窗口重开、错误重试、陈旧 PID/启动时间和回调隔离，以及现有 HID、按键序列
和租约测试。当前环境只有 Command Line Tools，没有 XCTest；使用已有源码断言
harness 编译生产源文件并执行测试体，不把它表述为标准 `swift test` 通过。
固件实际 main 的中央启动/隔离测试、Codex 像素等价测试和导航协议测试另行运行。

## 当前安装后的验收

需按当前安装签名重新核对 Companion 的输入监控和辅助功能，重启后看启动日志。
若旧条目显示开启但进程仍拒绝，移除该条目并重新添加当前安装的 app 后开启。
只处理 Companion；不修改其他应用权限或重置整个权限数据库。

对每个 Agent 分别验证未启动、已前台、已后台：左滑、必要时点中央、上/下/右；
然后切到其他 Mac 应用，确认手表保留选择、中央可重新唤起，且不误操作其他应用。
重复点按、左滑退出、休眠唤醒、重连和 Companion 重启需保持已有边界。
源码测试和构建通过不等同于上述物理 C152 验收；最终实机结果由当次日志和用户观察确认。

## build13：后台无窗口进程重新打开

用户进一步明确：有窗口时，唤起和上/下/右正常；只剩后台进程、没有桌面窗口时，
中央无反应。build12 对普通后台目标只调用进程激活，这不会要求应用恢复已关闭窗口。
新增回归用例在 build12 实际状态机上失败（`codexOpening != codex`）。

build13 将四个 Agent 的有效中央启动/唤起统一为打开应用请求，复用实际运行 bundle，
设置 `createsNewApplicationInstance = false`，保留 PID/启动时间和真实前台就绪确认。
已在前台的现有控制和左滑仅选择策略保持不变。SUPER 未知窗口状态仍不是无窗口证据，
但显式中央操作现在可以发出打开请求，不再停留在仅激活进程的分支。

本补丁的关键实机判据是：关闭 Agent 最后一个窗口但保留进程，左滑进入其手表桌面，
中央能重新打开窗口，随后上/下/右可操作。更新构建与权限检查后再记录结果。

build13 的 Release 构建通过，116 个生产源码断言测试体均通过；已安装并核对二进制
与候选包一致。安装后重启仍报告两项权限未有效授权，尽管系统开关显示开启。
当前等待刷新已有授权并完成上述无窗口实机验收；不能将构建与回归通过视为修复验收完成。

按用户授权重新添加当前安装程序的辅助功能和输入监控两项记录后，build13 新进程
启动确认 `导航权限：辅助功能=已授权`、`StopWatch HID 已连接`，同次启动无输入监控
拒绝提示。当前授权检查已通过，无窗口恢复和物理方向操作等待用户反馈。

本次用户反馈仍为“部分异常”，待补充具体 Agent 和失败步骤。当前已授权进程的
启动记录之后新增四次桌面切换等待超时；该次测试无可用的限时导航阶段日志，
不能据此确定超时分别属于哪个 Agent。build13 物理验收未通过，继续定位。

## build14：窗口关闭和迟到就绪

用户明确：SUPER 正常；DeepSeek 首次恢复慢、再次关窗后提示滞后；Hermes 窗口已前台
仍需再点中央。build13 仅检查 SUPER 的实际窗口，DeepSeek/Hermes 无窗口但进程仍前台时
会继续显示操作状态；而超过三秒的唤起进入错误状态后，后续真实窗口就绪也被屏蔽。

三个新增回归用例在 build13 上分别复现：关窗后未阻止导航、未知窗口状态误判可操作、
Hermes 就绪后仍停留错误状态。build14 将现有有界 AX 窗口检查扩展到三个快捷操作桌面，
每秒同步关窗状态；错误状态保留重试入口，同时允许实时确认所选前台窗口就绪后恢复。
不自动重发打开请求，陈旧回调仍无效，左滑离开后不会被旧请求恢复。
Codex 原仪表盘和输入路径保持原有行为。

只剩一个 DeepSeek 主实例被 NSWorkspace 登记；同一路径的另一进程未被登记为第二个
应用实例，因此不能把慢速恢复直接归因于多个主实例。应用自身重建窗口耗时与 Companion
状态同步耗时需分别观察，源码测试不证明应用窗口能够更快创建。

build14 的 119 个生产源码断言测试体及 Release 构建通过，已安装并核对候选包哈希。
按已有授权重新添加辅助功能和输入监控、重启后，新进程记录辅助功能已授权、HID 已连接，
同次启动无输入监控拒绝提示。当前等待 DeepSeek/Hermes 重复关窗恢复、单次中央点击后
方向操作及 SUPER 回归的实机反馈。

build14 本轮实机反馈仍为“有异常”，具体步骤待补充。限量日志确认 DeepSeek 的
23 次方向序列通过权限检查并提交；120 条阶段日志上限已用完，未采集到 Hermes
阶段，因此不能用该日志判断 Hermes 是否成功。授权生效后的进程另记录两次未就绪超时。
这仍不是完整实机通过记录。

用户进一步明确本轮结果：DeepSeek、SUPER 已完全正常；Hermes 首次中央唤起桌面后，
仍提示 `tap to retry`，上/下/右被阻止，第二次中央点击后才能操作。当前剩余问题限定为
Hermes 的首次窗口焦点就绪判定，build14 整体物理验收尚未通过。

## build15：Hermes 重建窗口缺少焦点句柄

本轮受控复现中，已授权 Companion 的 Hermes 焦点函数多次读取 FocusedWindow、
MainWindow 返回 `kAXErrorNoValue (-25212)`；该函数仅在所选进程确为前台、窗口列表
已判为可用后调用。另有成功调用的查询、抬起和窗口比较均成功。调试断点增加了延迟，
采集不用于评价正常响应速度，调试器已撤除。

新增回归先在原窗口解析逻辑失败：有标准窗口、但两个焦点句柄均缺失时返回空。
build15 仅针对 Hermes，在两个句柄均明确缺失时，从最多四个窗口中查找所属进程的
未最小化标准窗口，随后复用原抬起和真实焦点确认。未知错误、错误进程和辅助窗口
均不能开启导航；DeepSeek、SUPER 与四桌面状态机保持 build14 行为。

124 个生产源码断言测试体通过（非 XCTest）；Release 构建、安装权限和单次中央
唤起后方向操作仍需分别验证，当前不能声明完整实机修复通过。

build15 Release 以 warnings-as-errors 构建通过（38.30 秒），已安装并核对候选签名哈希，
保留 build14 和原 LaunchAgent，未改动设备固件。按用户已有授权重新添加并开启两项
记录，重启新进程后辅助功能已授权、HID 已连接，同次启动无输入监控拒绝。
已移除诊断调试器；Hermes 连续两次关窗、单次中央恢复后的方向操作等待实机结果。

最终本轮实机反馈：用户针对上述 Hermes 连续关窗恢复验证回复“
不出现 tap to retry 了，功能正常了”。本轮已知异常验收通过：DeepSeek、SUPER 已在
build14 由用户确认完全正常，Hermes 的首次中央唤起重试门槛在 build15 由用户确认消失。
Codex 原前台导航已在前轮确认正常；未额外声称本轮重复完成四个 Agent 的全部冷启动场景。
