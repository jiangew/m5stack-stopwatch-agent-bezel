# Historical isolated canary candidate

This builder packages the pinned DeepSeek Harness `0.2.0-rc.2` extension for source review. The installed `0.2.1-rc.2` archive differs; current-version compatibility is unsupported. Nothing here installs an extension, edits an effective profile, restarts a Host, or enables stock native decisions. Installed app, runtime, device and physical acceptance remain separate gates.

The default builder and Loader runner require the installed archive SHA256 in `fixture-manifest.json`. They refuse a newer archive. The exported builder API rejects archive-path overrides; installed verification always reads the canonical installed app path. An explicit `--historical-source-fixture` flag permits historical source tests and candidate generation using the retained exact code fixture when the original archive is unavailable. It skips only installed archive verification; full 9,006-file Loader/addon fixture, 1,558-file native tree, module, patch and patched-output pins still apply. Provenance records this mode and `installedArchiveVerified:false`. This mode does not establish that the installed app can load the candidate.

```sh
node scripts/test_deepseek_native_loader.mjs STOCK_NODE_MODULES VERIFIED_FIXTURE --historical-source-fixture
node scripts/build_deepseek_native_candidate.mjs STOCK_NODE_MODULES VERIFIED_FIXTURE PRIVATE_SYNTHETIC_PROFILE NEW_OUTPUT CONFIG_JSON CONFIG_SHA256 --historical-source-fixture
```

All arguments are explicit. The profile and output parent must be owner-private directories (`0700`), and output must be new, inside that profile, and either temporary or ignored by Git. Generated directories use `0700`, files `0600`. No package installation or download occurs. Native/framework `node_modules` below the profile are refused rather than removed. Output verification regenerates destination-specific bytes from pinned inputs and rejects altered permissions, symlinks, peers, dependencies, scripts, provenance or extra files.

Configuration is a JSON object with `kind`, `entries`, `presetEntryId`, `approvalEntryId`, `canaryId` and `canaryEntryId`. `CONFIG_SHA256` is the SHA256 of `JSON.stringify(parsedConfiguration)`. `kind:synthetic` declares a test inventory; it is not an effective-profile inventory. The selected explicit ordinary preset and approval policy are cloned, with expressions and platform conditions retained. Exactly one ordinary Bash row is required. Persistent Bash, unknown configuration shapes, missing/duplicate rows and colliding IDs fail closed. Defaults and stock presets remain unchanged.

Only the new opt-in preset places the project approval service and foreground Bash in `cordis:group` with `isolate:{approval:true}`. Nested plugin URLs are absolute and bound to the output destination. The package contains three patched native modules and the small project policy-floor subclass, exact native peers, upstream licenses and a JSON-compatible YAML overlay. Bash's single sandbox import becomes `./sandbox.js`; separate before/after hashes record that packaging transform. All other peers resolve through the original Host's public resolver. No framework copy or substitute Loader is packaged.

The floor resolves `ctx.root.get('approval').effectivePolicy(session)` on each lookup. Root never, missing/self/unknown/throwing roots reject; explicit native session overrides keep their upstream meaning. The project native patch rechecks policy after a pending answer and before committing `approval/decided`, so a watch or UI answer cannot commit an allowed audit after policy tightens. Only the committed matching UUID audit resolves the adapter card.

Provenance pins the input/output trees, original archive lineage, addon, peer manifests, verified configuration, transformed bytes, generated files and project implementation content hashes. Content hashes identify the exact uncommitted implementation without claiming a circular Git HEAD. Relocating output requires regeneration, since both overlay URLs and provenance bind the destination. Generated native code, profile overlays and provenance must remain private and untracked.

The real Loader tests exercise the native runtime resolver, preset registry, module identity, isolation, live root floor, production Task2 owner, UI continuation, concurrent UUIDs, cancellation, expiry/disconnect/disposal, and overlay removal/baseline recovery. Shell execution and OS activation are inert test boundaries; no model runs. Existing live agents retain their mounted preset revision until disposal, even after the overlay is removed. Deployment requires effective-profile inventory, independent review, compatible installed inputs and separate installed-runtime acceptance.
